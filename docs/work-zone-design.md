# 日常工作（Work Zone）模块设计

> 版本：v0.2 · P0 已落地
> 目标读者：本工具使用者（本机单用户、自用）
> 关联代码：`backend/work.py` · `frontend/`

---

## 0. 一句话

在现有「知识库 + 任务看板 + 日报周报」之上，新增一个**以"上班"为主线的日常工作模块**：
需求进来 → 设计出方案 → 拆解执行 → 修 bug → 留下进度与结论，全程可追溯；并支持把**历史设计文档 / 需求文档批量导入**，沉淀成可检索的资产。

---

## 1. 现状缺口（为什么要做）

现有四个模块各自成立，但拼不出"我手上的活儿现在到哪一步了"：

| 现有模块 | 能回答 | 答不了 |
|---|---|---|
| 知识库 | 文件在哪、内容是什么 | 这是"哪个需求"的文件、做到哪步了 |
| 任务看板 | 有哪些 TODO 卡 | 需求/bug 的层级关系、来源、影响范围 |
| 日报 / 周报 | 今天改了哪些文件 | 今天**推进了哪个需求**、修了**哪个 bug** |
| 检索 | 关键词在哪出现 | 按"工作项"检索 |

**核心缺口三条**：

1. **没有"工作项"这个概念** —— 需求、Bug、设计文档是三种不同生命周期的东西，现在都只能塞进扁平的 TODO 卡。
2. **没有进度留痕** —— 状态从"设计中"变成"开发中"这一刻，没有任何记录，月底回忆全靠翻聊天记录。
3. **历史内容进不来** —— 以前的详细设计、需求文档散在磁盘各处，无法沉淀、无法检索、无法复用。

---

## 2. 设计原则

### 2.1 一套文件，两种视图（最关键）

**日常工作不新造一套数据。** 它给 `vault/work/` 下的 Markdown 加一层**结构化 frontmatter**，然后提供两种看法：

- **知识库视图** = 按目录树看（完全不变，文件原样）
- **日常工作视图** = 按"工作项"看（需求 / 设计 / 开发 / Bug / 约定）

好处：Markdown 永远是唯一真相源 —— 随时能用任何编辑器改、能备份、能进 git（若你愿意）、能被 FTS5 检索、能被 AI 直接读。

### 2.2 进度靠文件，不靠数据库

状态变更**自动往正文追加一行时间线**，而不是写在 SQLite 里。数据库丢了不影响历史，换台机器把 `vault/` 拷过去进度还在。

### 2.3 零依赖

延续现有技术选型：后端只用 Python 标准库（含用 `zipfile` + `xml.etree` 解析 `.docx`，**不需要 python-docx**），前端零构建。

## 3. 信息架构

### 3.1 侧边栏（主菜单 + 子菜单）

```
工作区                        ← 现有功能分组
  概览 / 知识库 / 检索 / 任务看板 / 日报·周报

日常工作                      ← 新增：一个主菜单 + 六个子菜单
  总览
  需求
  设计
  开发
  Bug
  约定
```

> 命名区分：**工作区 = 软件的功能分组**，**日常工作 = 你上班干的活**。
> 采用"主菜单摊开子菜单"的形态而非单入口 + 内部 tab —— 少一层点击，一眼看清手上分几摊事。

### 3.2 子菜单职责

**一个子菜单 = 一个 `type` 过滤视图**，底层是同一批 Markdown 文件，不额外存一份数据。

| 子菜单 | 装什么 | 数据来源 |
|---|---|---|
| **总览** | 今日焦点、进行中、卡点、本周统计 | 全部 work 文件聚合 |
| **需求** | 需求条目：编号 / 来源 / 优先级 / 状态 | `type: requirement` |
| **设计** | 详细设计、方案、评审记录；可从需求一键生成设计骨架 | `type: design` |
| **开发** | 开发任务与改动记录：涉及文件、SQL、页面配置、提测包 | `type: dev` |
| **Bug** | 缺陷跟踪 + **Bug 分析**（详见 3.3） | `type: bug` |
| **约定** | 工作习惯与纪律卡片墙 | `type: convention` |

各子菜单统一布局：**左侧列表 + 右侧详情**（详情 = 字段编辑区 + Markdown 正文 + 进度时间线）。

### 3.3 Bug 记录（精简版）

Bug 详情页的正文**只保留两个固定区块**，够用、不啰嗦：

| 区块 | 说明 |
|---|---|
| **原因** | 为什么会这样（排查出来的根因） |
| **方案** | 怎么改的（改了哪段代码 / SQL / 配置） |

其余内容（现象、影响范围、验证结论）**不预设区块**，需要时自己在正文里补，不强制填。

> **可选字段「定性」**：frontmatter 里留一个下拉（`缺陷` / `需求变更`），默认留空。
> 它不进正文、点一下只要一秒，却能在"这到底该只改代码、还是该走需求变更流程"上留下判断依据（踩过把需求变更当 bug 修的坑）。觉得多余随时砍掉。

### 3.4 一条链，不是四份孤立数据

需求 → 设计 → 开发 → Bug 通过 `parent` / `refs` 字段串成一条链：

```
REQ-012 导出表字段对齐
  ├─ DES-003 字段映射设计       (parent: REQ-012)
  ├─ DEV-021 改 SQL + 页面配置   (parent: DES-003)
  └─ BUG-007 统计口径除零      (refs: [REQ-012])
```

详情页底部显示「上游 / 下游」，点击直接跳转 —— 既能按你的习惯分门别类地看，又不会看散。

## 4. 数据模型

### 4.1 目录结构

```
vault/work/
├── _conventions/                    # 工作习惯与纪律
│   ├── 交付文件改动纪律.md
│   ├── bug-只改代码纪律.md
│   └── 对比报告约定.md
├── _inbox/                          # 导入后的待整理区
├── <project>/                       # 一个项目 / 业务线一个目录
│   ├── _project.md                  # 项目元信息
│   ├── req/                         # 需求
│   │   └── REQ-012-导出表字段对齐.md
│   ├── bug/                         # 缺陷
│   │   └── BUG-007-统计口径除零.md
│   └── design/                      # 设计文档
│       └── DES-003-地址归一化设计.md
└── ...
```

### 4.2 Frontmatter Schema

**通用字段**

```yaml
---
id: REQ-012                    # 自动生成，全局唯一
type: requirement              # requirement | design | dev | bug | convention | note
title: 导出表字段对齐
project: <项目代号>             # 对应一级目录名
status: designing
priority: high                 # high | medium | low
owner: <使用者>                 # 留空亦可；不要写真实姓名
created: 2026-09-27
updated: 2026-09-27
tags: [report, export, sql]
refs: [BUG-007]                # 关联工作项 id
---
```

**状态机**

```
需求  backlog → analyzing → designing → dev → testing → staging → released
                                        ↘ paused / dropped

Bug   open → locating → fixing → verifying → closed
                                        ↘ wontfix
```

**Bug 专属字段**

```yaml
severity: major                # blocker | major | minor | trivial
verdict:                       # 定性：缺陷 | 需求变更（可选，默认留空）
```

> 正文只写「原因」「方案」两块（见 3.3），其余不设固定字段，保持轻量。

### 4.3 正文骨架（模板自动生成）

**需求 / 设计 / 开发**

```markdown
# REQ-012 导出表字段对齐

## 背景 / 需求描述
## 方案设计
## 影响范围
## 进展            ← 后端自动追加，不要手改
- 2026-09-27 09:20  状态 designing → dev（使用者）
- 2026-09-26 17:05  创建（来源：产品评审）
## 结论 / 复盘
```

**Bug（精简：只有原因和方案）**

```markdown
# BUG-007 统计口径除零

## 原因
## 方案
## 进展            ← 后端自动追加，不要手改
- 2026-09-27 10:30  状态 open → fixing（使用者）
```

> **进展区是"工作进度"的真相源**：每次状态流转自动追加一行带时间戳的记录，月底写汇报直接顺着读。

## 5. API 设计

沿用现有 `_api()` 分发风格，新增：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/work/board` | 日常工作聚合（今日焦点 / 进行中 / 卡点 / 统计） |
| GET | `/api/work/items?type=&project=&status=&q=` | 工作项列表 |
| GET | `/api/work/item?path=` | 单个工作项（字段 + 正文） |
| POST | `/api/work/item` | 新建（自动编号 + 模板 + 骨架） |
| PUT | `/api/work/item` | 更新字段（**状态变更自动追加时间线**） |
| POST | `/api/work/import` | 批量导入（指定 project + type） |
| GET | `/api/work/conventions` | 工作约定列表 |
| GET | `/api/work/progress?days=7` | 进度聚合 |

新增后端模块 `backend/work.py`（约 250 行），负责：扫描 `vault/work/` → 解析 frontmatter → 结构化 → 聚合。**文件量小，直接扫盘，不建新表**，避免双写不一致。

## 6. 导入能力（你重点提的）

### 6.1 三种入口

1. **粘贴 / 拖拽**：把 Markdown 拖进「日常工作」→ 落到 `_inbox/` 或直接选项目 + 类型归档
2. **本地路径批量导入**：填一个目录（如历史文档目录）→ 扫描 `.md / .txt / .docx` → 出预览列表 → 勾选 → 一键导入
3. **单文件 docx**：后端用标准库 `zipfile` 解开 + `xml.etree` 抽 `<w:t>` 文本 → 转 Markdown 骨架

### 6.2 导入时自动做的事

- 抽标题（优先 H1，其次文件名）
- **猜类型**（文件名含"需求"→ requirement，"设计"→ design，"bug/缺陷/问题"→ bug，否则 note）
- 生成 frontmatter 骨架，状态默认 `backlog`（等你确认后再流转）
- **原文完整保留在正文**，只做结构包裹，不做有损裁剪
- **幂等**：同名不覆盖，自动加序号或提示确认

### 6.3 为什么值得做

你过去几年的详细设计、需求、复盘，是**最有价值的私有语料**。导进来之后：

- 检索得到（FTS5 + 语义）
- 能被 AI 读（以后接大模型做"这个需求跟以前哪个设计像"）
- 下次写详细设计，有模板可循

## 7. UI 设计

### 7.1 页面结构

六个子菜单共用同一套骨架，差异只在「列表区形态」和「详情区字段」：

```
┌─ 列表区 280px ─────────┬─ 详情区 ──────────────────────┐
│ [+ 新建]   [筛选 ▾]     │  REQ-012 导出表字段对齐        │
│                        │  [开发中] [高] [<项目 A>]      │
│ ▾ <项目 A>          (5)│ ──────────────────────────── │
│   · REQ-012 开发中  ●  │  字段编辑区（状态 / 优先级 / 标签）│
│   · BUG-007 修复中  ▲  │ ──────────────────────────── │
│ ▾ <项目 B>          (2)│  Markdown 正文（阅读 / 编辑）    │
│   · DES-003 已定稿     │ ──────────────────────────── │
│                        │  进展时间线                    │
└────────────────────────┴────────────────────────────────┘
```

| 子菜单 | 列表区形态 | 详情区特殊区块 |
|---|---|---|
| **总览** | 指标卡 + 今日焦点 | — |
| **需求** | 按状态泳道（看板） | 来源、验收标准 |
| **设计** | 文档列表 | 方案、表结构、影响范围 |
| **开发** | 任务泳道 / 列表 | 涉及文件、SQL、提测包 |
| **Bug** | 列表，严重度着色 | **原因 / 方案**（见 3.3） |
| **约定** | 卡片墙 | 全文 |

### 7.2 复用现有设计语言

- 卡片 `.card`、徽章 `.badge`、泳道 `.kanban`、树 `.tree`、编辑器 `.editor-pane`
- Bug 严重度着色：`blocker` 红 / `major` 橙 / `minor` 黄 / `trivial` 灰
- 不引入任何新的设计体系，保持 Linear 观感一致

## 8. 与现有模块的关系

| 模块 | 关系 |
|---|---|
| **知识库** | 同一批文件，按目录树看 —— 零重复存储 |
